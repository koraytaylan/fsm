## 0000 — Orientation: the four hard facts that shape everything

This plan adds a process that runs real work against the world's computers. Four pre-existing engine facts decide its shape; do not fight them. Each was read out of the code named beside it — check the code, not your memory of it.

- **The store is single-writer.** Every mutator (`ack_effect_outcome_on`, `send_event_stamp_on`, `poll_instance_deadline_on`, …) calls `ensure_writable()` (`store/commit.rs`) and the writer holds an advisory `File::try_lock` on `<data_dir>/journal/LOCK` for the lifetime of the `Store` (`journal_io/paths.rs::acquire_lock`, kept in `Journal::_lock`). Only one open writer per data dir, *including a second open in the same process*. `Store::open_read_only` sets `_lock: None`, creates no files, and coexists with a writer, returning one consistent hash-verified journal prefix per open.
- **Effects never drive transitions.** `ack_effect` clears a pending effect and nothing else; `outcome: "failed"` leaves the instance exactly where it was. Advancement is caused only by an explicit `send_event` (a domain event the machine already declares) or an explicit `poll_instance_deadline`. The executor therefore *reacts to* records and *issues* acks/events the spec already permits — it never originates a state change the machine didn't model.
- **A pending effect is an opaque id.** `instance_view` renders `effects_pending` as an array of `{instance_id}/{seq}/{k}` strings and nothing else (`store/view.rs`, `store/reconstruct.rs::view_at`); no journal record body carries an emitted effect's **name** or its evaluated **args** (`store/instance/send.rs`, `store/instance/poll.rs`), and `EmitTrace` (`fsm_core::trace`) carries `effect` and `k` but not the arg values. A human host knows what `inst-ol1/3/0` means by reading the machine; a mechanical executor must *derive* it. Workstream 0037 does exactly that, and nothing downstream may assume the store hands it a name.
- **The journal is the executor's only memory.** `StoreState::dedup` is a public `BTreeMap<request_id, RequestSlot>` folded from the journal, so "did I already issue this?" is answerable from a read-only open for any *derived* `request_id`. Every piece of executor state that must survive a kill is therefore reconstructible: `effects_pending` says what still needs running, and `dedup` says what has already been written. Nothing may live only in process memory.

The consequence: an executor is a **second process** holding the journal single-writer lock, watching via the read-only path, and writing acks/events/polls. The MCP `serve` process is a peer that *also* wants to write acks. Plan 0008 must therefore make these two coexist without ever double-writing, and must never require the LLM to be online for the workflow to progress.

## 0036 — Crate & handler config

New crate `crates/fsm-execute` (task `3601`). It is a **library** (like `fsm-store`, not like the `fsm-cli` binary) so the scheduler, watcher, and runner are unit-testable in-process; `fsm-cli` links it and exposes it as the `fsm execute` subcommand (workstream 0039).

- Workspace `Cargo.toml` `members` gains `"crates/fsm-execute"`. New `crates/fsm-execute/Cargo.toml` carries `edition.workspace = true`, `rust-version.workspace = true`, `version.workspace = true` (all crates share one version, per `docs/API-POLICY.md`), `license.workspace = true`, `repository.workspace = true`, and `[lints] workspace = true` (which brings `unsafe_code = "forbid"` and the clippy print denies). Its only path dependencies are `fsm-core` and `fsm-store` — matching the zero-dependency posture; it must not add third-party crates.
- **A fifth crate is a registered fact, not just a directory.** `crates/fsm-cli/tests/zero_deps.rs` hard-codes `WORKSPACE_CRATES` and panics on any package the resolved graph adds or drops, and it shells `cargo metadata --locked`, so the committed `Cargo.lock` must gain the crate in the same commit or that test fails on a locked graph. Both files belong to task `3601`; CI runs the test as its own `zero-deps` job and `docs/RELEASE.md` names it in the gate.
- `crates/fsm-execute/src/lib.rs` declares `#![forbid(unsafe_code)]` and `pub mod config; pub mod effect; pub mod rid; pub mod watch; pub mod sched; pub mod run; pub mod error;` plus a thin `pub mod service;` that composes them into a runnable loop (`tick` from task `3802`, `run` from task `3901`). Public error type `pub struct ExecError { pub code: &'static str, pub message: String, ... }` mirrors `ErrorObj`'s philosophy (namespaced code + message + hint) so `fsm-cli` can render it through the same error channel; it does **not** reuse `ErrorObj` (a store type) to keep `fsm-execute` honest about its own failure domain. Codes live under the `exec/*` namespace and are appended to the crate's own `ALL_CODES`-style table, *not* `fsm_core::error::ALL_CODES` (engine codes only — see task `4101` for how the doc references them without polluting the engine appendix). The closed set, each with the one place that raises it:

  | code | raised by |
  |---|---|
  | `exec/config` | handler-table parse/validation and argv substitution (`3602`) |
  | `exec/effect_unresolved` | an effect id whose name/args cannot be re-derived from the journal (`3701`) |
  | `exec/unhandled_effect` | a pending effect with no handler — logged, default-deny (`3704`) |
  | `exec/spawn` | `Command::spawn` io failure, naming `argv[0]` (`3801`) |
  | `exec/timeout` | an inflight handler killed past its deadline (`3801`/`3802`) |
  | `exec/cancelled` | an inflight handler killed because its instance was cancelled (`3801`/`3802`) |
  | `exec/store` | any `ErrorObj` from an open, ack, send, or poll, preserved in `details` (`3703`/`3802`) |
  | `exec/mode` | `--exclusive` started against a data dir another process already holds (`3902`) |

The handler table (task `3602`) is the **security boundary** of the whole plan. It is a single operator-owned JSON file, parsed once at executor start, that closes the set of commands the executor can ever run.

- **Format `fsm.handlers/1`** (`docs/SPEC.md` does not grow this; it is an executor config format, documented in `docs/EMBEDDING.md` by task `4101`, not a machine-definition key). Examples across this plan stay in the repo's neutral business-process vocabulary (`order_lifecycle`, `invoice_matching`, `case_review`, `expense_approval`) — no cloud-vendor or product names anywhere in the fixtures or the docs:

  ```json
  {
    "format": "fsm.handlers/1",
    "handlers": [
      {
        "effect": "request_confirmation",
        "argv": ["/usr/local/bin/notify-supplier", "--order", "{order_id}", "--quiet"],
        "timeout_ms": 120000,
        "on_ok": { "event": "confirmed", "payload": {}, "stamps": ["at"] },
        "on_failed": { "event": "confirmation_failed", "payload": { "reason": "handler" } }
      }
    ]
  }
  ```

- `struct HandlerTable { handlers: BTreeMap<String, HandlerSpec> }`; `struct HandlerSpec { effect: String, argv: Vec<String>, timeout_ms: i64, on_ok: Option<Advance>, on_failed: Option<Advance> }` with `struct Advance { event: String, payload: Value, stamps: Vec<String> }`. Parse via `fsm_core::json::parse(src.as_bytes(), &JsonLimits::DEFAULT)` — never a third-party deserializer — and validate structurally before returning:
  - top-level `format` must be exactly `"fsm.handlers/1"`;
  - `handlers` is a non-empty array of objects, each with required string `effect`, non-empty `argv` array of strings, and positive-integer `timeout_ms`;
  - `effect` names must be unique across the table (duplicate → `exec/config`);
  - every `{placeholder}` in `argv` must be a well-formed single identifier (validated by scan, not regex — no regex dep): `{` `}` balanced, name `[a-z_][a-z0-9_]*`;
  - a handler whose `argv` is empty, or whose `effect` is empty, or whose `timeout_ms` is missing/non-positive → `exec/config` with the offending index in `details`;
  - `on_ok`/`on_failed`, when present, are objects with a non-empty string `event`, an optional `payload` **object** (default `{}`), and an optional `stamps` array of non-empty strings (default `[]`), passed straight to `send_event_stamp_on`'s `stamps` argument so the store fills those timestamp fields from the injected clock. Nesting them is deliberate: a payload or a stamp list without an event is unrepresentable rather than a validation rule someone forgets.
- **Substitution is data-in, argv-out — never a shell.** `fn substitute(argv: &[String], args: &BTreeMap<String, Val>) -> Result<Vec<String>, ExecError>` replaces each `{name}` with the *string form* of the effect argument of that name — `fsm_core::replay::ctx_val_string` (i.e. `Val::canonical_string`), the same rendering the rest of the workspace persists context with, so ints, decimals, bools, and timestamps are exact and strings are verbatim. **No shell is ever spawned** — execution is `std::process::Command::new(argv[0]).args(&argv[1..])` so a substituted value can never be re-split or glob-interpreted by `/bin/sh`. A placeholder naming an effect arg absent at run time is a run error (surfaced as a handler failure and acked `failed`), not a config error, because effect-arg sets vary per emit.
- **Default-deny.** An effect emitted by the machine whose name has **no** handler is never improvised. It is reported as `exec/unhandled_effect` (logged once per effect from the scheduler's `unhandled()` list), and the executor takes **no** transition and sends **no** event for it — the instance simply waits, exactly as documented for the outbox. This is a deliberate stall, not a failure: the fix is to extend the table, and the machine's own deadline (if modeled) decides whether abandonment/rollback fires. The executor's job is to refuse to guess.
- The table is loaded and **validated fully at startup**; a parse or structural error aborts the run before any store is opened. There is no hot reload in v1 — restarting the executor with a new table is a deliberate, journaled event (the acks it then writes reference the new handlers).

## 0037 — Effect resolution, watcher & scheduler

Resolving a pending effect id to a **name and args** (task `3701`) is the first thing to build, because §0000's third fact means nothing else in the plan can start without it. It is a pure function over a read-only store, in `crates/fsm-execute/src/effect.rs`.

- `pub struct PendingEffect { instance_id: String, effect_id: String, effect_name: String, args: BTreeMap<String, Val>, emitted_seq: u64, k: u32 }` and `pub fn resolve(store: &Store, effect_id: &str) -> Result<PendingEffect, ExecError>`.
- The id shape `{instance_id}/{seq}/{k}` is the whole input: split on the **last two** `/` (an instance id may not contain `/`, but split from the right regardless), parse `seq` and `k`, and find the record with that `seq` in `store.records` (a public field). A malformed id, a missing record, or a record whose `instance_id` differs → `exec/effect_unresolved`.
- Re-derive by replaying that one record against the state *before* it: fold `store.records` filtered to `seq - 1` with `fsm_core::replay::fold_with(.., &mut NopSink)`, then re-run the pure engine entry point that wrote it, using the record's own body and **`rec.ts`** — never a clock, because SPEC pins every record's timestamp to the exact `now_ms` the pure call received, so this replay is exact:
  - `EventApplied` → `step(&m.compiled, &m.tree, pre_inst, event, payload, rec.ts, &mut Budget::new(MAX_EVAL_TICKS))` → `Outcome::Applied(a)` → `a.effects`;
  - `InstanceCreated` → `create(&m.compiled, &m.tree, &overrides, rec.ts)` with `overrides` read back from the record body through `fsm_core::replay::parse_ctx_json` against the machine's declared context types;
  - `DeadlineApplied` → `poll_deadline(&m.compiled, &m.tree, pre_inst, rec.ts, &mut budget)` → its `transition.effects`;
  - any other record kind → `exec/effect_unresolved`.
- Select the emit whose **`k` equals the id's `k`** (never by vector index) and return its `name` and `args`. `fsm-store` already does exactly this replay privately for history rendering (`store/reconstruct.rs::reconstruct_applied`); this is the same technique against public API only, which is why no change to `fsm-core` or `fsm-store` is needed.
- Cost is one prefix fold per unresolved effect, so `resolve` is called **once per effect id** and the result is carried in the `Observation`; a small `BTreeMap<String, PendingEffect>` memo inside the watcher keeps a re-scan of a long-pending effect from re-folding.

Request IDs (task `3702`) are how the executor survives its own death. It **derives** every `request_id` deterministically from content it already knows, so a re-issue after restart replays rather than re-applies. They live in their own `crates/fsm-execute/src/rid.rs` because the scheduler composes them, the pipeline issues them, and the watcher's claimed-key set is compared against them — three callers, no owner among them.

- `fn ack_rid(effect_id: &str) -> String` → `format!("exec-ack-{effect_id}")` (effect_id is already `{instance}/{seq}/{k}`, globally unique);
- `fn event_rid(effect_id: &str, event: &str) -> String` → `format!("exec-ev-{effect_id}-{event}")`;
- `fn poll_rid(instance_id: &str, deadline: &str, due_ms: i64) -> String` → `format!("exec-poll-{instance_id}-{deadline}-{due_ms}")` (due_ms in the id so a *new* due gets a *new* key, matching SPEC's "a new request_id for a new observation").
- Because the store keys idempotency on `(request_id, content-fingerprint)` and the executor derives both from instance state, a crashed-and-restarted executor re-issuing an ack with the same content gets `duplicate: true` and never double-writes; a *changed* intent under a recycled id is refused as `req/request_id_conflict`, which surfaces as `exec/store` and halts that directive rather than silently replaying.
- One consequence to know before it surprises someone: the ack fingerprint covers the `result`, and `result` carries the handler's stdout. A single executor never re-acks an already-acked effect (the ack clears it from `effects_pending`, so nothing re-starts it), but **two** writers racing the same effect — an executor plus an embedded serve, say — would produce two acks with the same derived key and different captured output, and the second is refused with `req/request_id_conflict`. That refusal is the design working: it is exactly the collision the mode table (0039) exists to prevent, and it fails loudly instead of writing twice.
- The tests pin that the same inputs always produce the same ids and that distinct due-times produce distinct poll ids.

The watcher (task `3703`) is the only component that touches the store on the *read* side, and it uses only `Store::open_read_only`.

- `struct Watcher { data_dir: PathBuf, last_seq: u64, resolved: BTreeMap<String, PendingEffect> }`. `fn scan(&mut self) -> Result<Observation, ExecError>` opens a *fresh* read-only store each poll (cheap relative to subprocess cost; re-folds the journal prefix), reads `journal.last_seq`, and takes what the outbox needs straight from `store.state.instances` — `InstanceState`'s fields are public: `pending`, `status`, and `deadlines` (already a `name → due_ms` map of integers). **Not** through `instance_view`: that renders a whole response per instance, evaluates `enabled_events` under a step budget for each one, and hands back `due_ms` as a string to re-parse. The watcher needs none of it, and paying an enabled-event analysis for every instance four times a second buys nothing. `enabled_events` matters exactly once — in the pipeline, on the one instance it just acked (§0038).
- **Every instance, not only the running ones.** A transition into a terminal state emits its entry-block effects like any other, so a completed instance can hold pending effects — a final notification is the obvious modelling of it — and a watcher that filtered on `status == running` would silently never run them. The outbox is scanned for all instances; what *status* gates is the advance, not the work — and the pipeline gates it explicitly, because the two terminal statuses do not behave alike: a **completed** instance sits on a terminal leaf, so `enabled_events` reports nothing enabled and the question answers itself, while a **cancelled** instance keeps the configuration it had (cancel only sets the status), so its events still report as enabled and only `step` refuses — by journaling a rejection that burns the derived key. That asymmetry is why §0038's advance gate tests `status == running` as well as the event's status. Deadlines are polled for running instances only, because the engine rejects a poll against a completed or cancelled one.
- It returns `Observation { from_seq, to_seq, pending: Vec<PendingEffect>, settled: Vec<SettledEffect>, due_deadlines: Vec<DueDeadline>, cancellations: Vec<String>, claimed_request_ids: BTreeSet<String>, instance_states: BTreeMap<String, InstanceSnap> }`:
  - `pending` is **every** effect id currently in an instance's `effects_pending`, resolved through `effect::resolve` — not only the ones new since the last scan. The watermark is an optimization for logging, never the thing that decides work, because a restarted executor must see a long-pending effect on its very first scan.
  - `settled` carries `SettledEffect { instance_id, effect_id, effect_name, outcome, seq }` — the input to the advance-resume rule below. It needs the **name** like `pending` does, for the same reason and by the same `effect::resolve` call: the scheduler cannot find a handler for `inst-ol1/3/0`. Resolution works after the ack because it replays the *emitting* record, which the journal keeps forever.
  - `settled` is bounded, or it would grow without limit: include only acks of **running** instances (a terminal or cancelled instance has no enabled event to advance into) whose `seq` is **greater than that instance's latest `event_applied`/`deadline_applied` seq**. An ack the instance has already transitioned past cannot be the one that was interrupted, and its advance would be refused by the enabled-status gate anyway. In the interrupted case — ack written, advance lost — the ack *is* the instance's newest record, so the rule includes exactly what recovery needs, typically nothing or one entry.
  - `claimed_request_ids` comes from `store.state.dedup` (a public map, §0000's fourth fact) and is what makes "have I already written this?" answerable after a kill without any process memory. Copy only the keys with the `exec-` prefix: the full map holds one entry per request the store has *ever* served, and cloning that four times a second is a cost with no purpose — the executor only ever asks about its own derived keys.
  - `due_deadlines` carries `(instance_id, deadline_name, due_ms)` straight from `InstanceState::deadlines`, for entries at or past now on running instances only.
  - `instance_states` carries `InstanceSnap { status, pending: usize, deadlines: usize }` per observed instance — counts and a status, nothing that has to be hashed or rendered. It feeds the action lines and the status logging, and it is why a directive can name what it acted on without a second store open.
- **Re-open per scan, not a long-lived handle.** `open_read_only` returns one consistent prefix and records appended after it are visible on the next open; the watcher therefore treats each scan as a snapshot and never holds state that could go stale.
- The watcher performs **no writes and acquires no lock**, so it is safe to run while `fsm serve` (or any writer) is active. All error surfaces from opening/folding map to `exec/store` with the underlying `ErrorObj` preserved in `details`.

The scheduler (task `3704`) is the plan's brain and is **pure**: it decides what to do given an `Observation` and a `now_ms`, without ever spawning a process, touching the store, or reading a clock. Every case is unit-testable by handing it a fabricated observation and a chosen time.

- `struct Scheduler { table: HandlerTable, inflight: BTreeMap<String /*effect_id*/, Inflight>, issued_polls: BTreeSet<(String, String, i64)> }`; `fn on_observation(&mut self, obs: &Observation, now_ms: i64) -> Vec<Directive>`. It holds **no** clock: time arrives as `now_ms`, which is what makes every decision a pure function of its inputs. `inflight` tracks only what is running *in this process right now* (a child pid has no journal representation); every other decision is taken from the `Observation`, so a fresh process with an empty `inflight` reaches the same conclusions. A `Directive` is one of `Start { effect, argv, timeout_ms }`, `Kill { effect_id, reason }`, `PollDeadline { instance_id, deadline, due_ms, request_id }`, or `SendEvent { instance_id, effect_id, event, payload, stamps, request_id }`. Decision **tables**, not bespoke logic:
  1. for each `obs.pending` effect **with** a handler and no inflight entry and whose `ack_rid` is not in `claimed_request_ids` → `Start`, mark inflight with the deadline `now_ms + timeout_ms`;
  2. for each pending effect with no handler → nothing (default-deny; reported through `unhandled()` for the service loop to log as `exec/unhandled_effect`);
  3. for each `obs.settled` effect whose handler declares the matching `on_ok`/`on_failed` and whose `event_rid` is **not** in `claimed_request_ids` → `SendEvent`. This is the rule that makes a kill between ack and advance survivable: the ack is in the journal, the advance is not, and both facts are readable from a fresh open. It equally covers an effect a human acked from the CLI — the handler table declares that mapping, so the executor honours it.
  4. for each `due_deadline` whose `poll_rid` is not in `claimed_request_ids` and not in this process's `issued_polls` set → `PollDeadline`. `inflight` is keyed by effect id and holds no deadlines; the same-tick de-duplication needs its own `BTreeSet<(instance_id, deadline, due_ms)>`.
  5. for each inflight effect whose instance appears in `obs.cancellations` (a cancel event was journaled) → `Kill { reason: Cancelled }`;
  6. for each inflight effect past its deadline → `Kill { reason: Timeout }`, which the runner reaps into a `Killed` outcome and the pipeline acks `failed` (workstream 0038).
- Two invariants the scheduler enforces and the tests pin: **it never emits two directives for the same `effect_id` in one tick**, and **it never emits a directive whose `request_id` is already in `claimed_request_ids`** — the journal, not memory, is what prevents a repeat.
- **One clock, owned by the driver.** `service::run` (or a test) holds the single `Clock`, reads `now_ms` from it once per tick for the scheduler, and lends `&mut dyn Clock` to the pipeline for the store's `_on` mutators. Nothing else owns one. Tests inject `FixedClock`; production injects `SystemClock`. Time is data everywhere — there is no `Instant::now()` hidden in logic, and no component can disagree with another about what time it is.

## 0038 — Runner & ack

The runner (task `3801`) is the only component that spawns processes. It is deliberately thin: given a `Start` directive, run it; given a `Kill`, stop it; report a `RunOutcome`.

- **Capture to files, not pipes.** A piped child whose output exceeds the OS pipe buffer (~64 KiB) blocks on write until someone reads, and a runner that only drains after `try_wait` reports exit will never read — the handler hangs until its timeout kills it, and the plan's own "digest the full output" rule guarantees somebody eventually writes that much. Draining incrementally would mean a reader thread per stream; redirecting to a file means neither. The runner creates one scratch directory at startup (`std::env::temp_dir().join(format!("fsm-exec-{pid}"))`) and spawns each child with `.stdout(File)` / `.stderr(File)` over `<scratch>/<effect_id with '/' → '-'>.out|.err`, deleting both after capture and removing the directory on `Drop`.
- `struct Runner { scratch: PathBuf, children: BTreeMap<String /*effect_id*/, Child> }`. `fn spawn(&mut self, effect_id: String, argv: &[String]) -> Result<(), ExecError>` runs `Command::new(&argv[0]).args(&argv[1..])` with those two file redirections, records the child under the effect_id, and returns `exec/spawn` (naming `argv[0]`) on any io error. **No `exec` family call, no shell, ever** — the crate name `fsm-execute` is the domain verb from the docs, not the libc `exec(3)`.
- `fn poll(&mut self, effect_id: &str) -> Option<RunOutcome>` non-blockingly reaps finished children (`try_wait`), then reads back the two capture files into `BoundedBytes`. A child killed by a signal has no exit code; report it as `Completed { status: -1, .. }` rather than unwrapping a `None`. On a `Kill` it sends `child.kill()` (SIGKILL-equivalent on the platform), reaps, and reports `Killed`.
- `enum RunOutcome { Completed { status: i32, stdout: BoundedBytes, stderr: BoundedBytes }, Killed { reason: KillReason }, SpawnFailed { argv0: String } }` with `enum KillReason { Timeout, Cancelled }`. A timeout and a cancel are different facts about the run and the ack should say which; collapsing both into one `TimedOut` would journal a lie half the time.
- **Every outcome must produce a deterministic ack `result`** — `fn ack_result(&self) -> Value` — because the store fingerprints the ack over it and a re-issue with different content is a conflict, not a replay. `Completed` → `{"status": i32, "stdout": "...", "stderr": "..."}`; `Killed` → `{"status": -1, "error": "exec/timeout" | "exec/cancelled"}`; `SpawnFailed` → `{"status": -1, "error": "exec/spawn", "argv0": "..."}`. No timestamps, durations, or pids in that object — those differ between the write and any later replay of it.
- `BoundedBytes` caps captured output well under the journal's `MAX_PAYLOAD_BYTES` (64 KiB canonical) so the ack payload can't blow the per-record ceiling: capture at most `ACK_OUTPUT_CAP = 4096` bytes of stdout, then append a digest (`fsm_core::sha256::sha256` + `to_hex`) of the **full** output if it exceeded the cap, so the journal keeps a tamper-evident reference to large output without storing it (mirroring SPEC §Payload size's "journal a digest"). Stderr truncated similarly. Two capped streams plus their digests stay far under the ceiling even when every byte escapes to six.
- **Handler output is bytes; a journal record is canonical JSON.** `BoundedBytes::to_json_string()` is the one conversion: truncate at or below `ACK_OUTPUT_CAP` **on a UTF-8 character boundary** (never mid-sequence), then render through `String::from_utf8_lossy`. A handler that writes binary or invalid UTF-8 therefore produces a lossy-but-valid string plus the digest of the true bytes — the ack never fails to journal because of what a handler printed.
- **Orphans are a boundary, not a bug to hide.** `impl Drop for Runner` kills and reaps every remaining child and removes the scratch directory, so a clean shutdown leaves nothing behind. No *signalled* shutdown can run that code — not `kill -9`, and not Ctrl-C either, because Rust's default handler terminates without unwinding: the children are re-parented and keep running, the scratch files stay, and the next executor **cannot adopt them** — it sees the effect still pending and starts a fresh one. That is precisely the at-least-once boundary this plan claims (§0041), and the compensating-effect advice is how a machine copes with it. No pid file, no adoption protocol, no pretending otherwise.
- The runner owns no policy — success/failure mapping is the ack pipeline's job. It only guarantees: a spawned child is always either reaped, killed, or documented as an orphan of a killed executor, and `poll` is the sole place `try_wait` is called.

The ack-and-advance pipeline (task `3802`) is the one component that **writes**. The tick opens the writer and lends it; the pipeline maps a `RunOutcome` to journaled reality through the store's own idempotent mutators, in exactly this order:

1. `ack_effect_outcome_on(clock, instance_id, effect_id, &ack_rid(effect_id), outcome, Some(run_outcome.ack_result()))` where `outcome = "ok"` iff `RunOutcome::Completed` with `status == 0`, else `"failed"` — `Killed` and `SpawnFailed` ack `failed` through their own deterministic `ack_result()` forms. An `ack` of a not-pending effect (e.g. another path already settled it) journals a `request_rejected` **record** and returns `Err(ErrorObj { code: "req/field_unknown", .. })` — that exact code, not a `request_rejected` one; match on it, treat it as benign, log, and return `SettleOutcome::AlreadySettled`. The rejection also claims the derived `ack_rid`, so a later re-issue replays the same benign rejection rather than writing anything.
2. On an `ok` ack the pipeline then issues the **advance event** the machine declares, if the handler declared one: `send_event_stamp_on(clock, instance_id, &adv.event, &mut payload, &event_rid(effect_id, &adv.event), Some(ack_seq), &adv.stamps)` over a clone of the table's payload, since the store stamps into it. **Where does `event` come from? From the handler table, naming an event the machine already declares.** Know the two failure shapes before an operator meets them: a payload whose *shape* the event rejects fails in `validate_event` **before** anything is journaled and **without** consuming the key, so correcting the table and letting the next tick retry works cleanly; a payload that validates but loses on a **guard** journals an `event_rejected` record and claims the key, so that advance never fires again for that effect — which is precisely what the enabled-status rule below exists to avoid. With no `on_ok`, the pipeline takes **no** advance action and returns `SettleOutcome::AckedNoAdvance`, leaving progression to a deadline or an external event. A `failed` ack uses `on_failed` the same way; undeclared failure again stalls deliberately.
3. **The advance gate is two conditions, and "enabled" is a status rather than mere presence.** Re-read the instance with `store.instance_view(instance_id, None, None)` after the ack — the ack response itself carries no `enabled_events` — then send only when **both** hold: the instance's `status` is `running`, and the named event's entry has `status == "enabled"` (or `"depends_on_payload"` with a non-empty `payload`/`stamps` on the advance). Presence is the wrong test because `enabled_events` lists *every* declared event with a status of `enabled`, `disabled`, `depends_on_payload`, `preempted`, or `preempted_maybe` (`fsm_core::analyze::EventStatus`). And the status check alone is the wrong test because `enabled_events` reasons from the configuration, not the lifecycle: cancel leaves the configuration untouched, so a **cancelled** instance still reports enabled events, and only `step` refuses — journaling an `event_rejected` and burning the derived key for good. Anything else: send nothing, return `AckedNoAdvance`, log the status. The executor never fires an event it expects the engine to reject.
4. `expect_seq` on the advance send is set to the `seq` returned by the ack, giving optimistic-concurrency failure (`req/seq_mismatch`, retryable) if anything else advanced the instance between ack and send; the pipeline retries the *same* `request_id` after re-reading with the fresh seq. SPEC sanctions exactly this: `expect_seq` is excluded from the request fingerprint and `req/seq_mismatch` is unjournaled and consumes no `request_id`.
5. `poll_instance_deadline_on(clock, instance_id, &poll_rid(...), None)` for each `PollDeadline` directive, honouring SPEC: a `NotDue` observation is journaled and its `request_id` claimed, so draining multiple due deadlines is one poll each, retried identically on re-issue. The store applies **at most one** due deadline per call and picks it by `(due_ms, document index)` — it takes no deadline name — so the name in `poll_rid` is a key ingredient, not a selector, and two due deadlines mean two directives with two keys.
6. A `SendEvent` directive from the scheduler's advance-resume rule (0037 rule 3) runs step 2's send **without** a preceding ack: the ack is already in the journal from a previous life, `expect_seq` is `None`, and the derived `event_rid` makes a re-issue a `duplicate: true` replay rather than a second transition.
7. Whatever the outcome — advanced, `AckedNoAdvance`, `AlreadySettled`, or an `exec/store` failure — the tick calls `scheduler.complete(effect_id)` afterwards, and it does the same when `spawn` itself fails. An effect that is marked in-flight and never cleared is invisible to decision rule 1 for the life of the process, which is the one way this design can wedge itself; clearing on *every* terminal path is what prevents it.

Every journaled outcome — ack, advance event, poll, and every rejection — lands in the tamper-evident chain, so `instance_history --trace` reconstructs the executor's whole night without the executor keeping any log of its own.

## 0039 — CLI & serve integration

The `fsm execute` subcommand (task `3901`) composes the library into the runnable process. It lives in `fsm-cli` (a sibling to the existing subcommands) so there is still one binary to install.

- `fsm execute --handlers <file>`: parse+validate the handler table (abort pre-store-open on `exec/config`), then run `service::run(...)` — the loop: `watcher.scan()` → `scheduler.on_observation()` → for each directive `runner.spawn/poll` or `pipeline.settle/poll` → sleep `poll_interval_ms` (default 250, flag) → repeat. The loop honours the same blocking-no-async posture as the rest of the workspace; it is a plain `loop` with `std::thread::sleep`, not a runtime. `--data-dir` is **already a global flag** with an `FSM_DATA_DIR` fallback (`args::resolve_data_dir`); `execute` inherits it like every other subcommand rather than declaring its own.
- The executor keeps a **read-only watcher handle** for scanning and opens a **separate writer `Store` only when a tick has something to write**, then drops it — opening the writer takes the single-writer advisory lock, so the CLI must not hold it across sleeps (or nothing else can ever write). The write path is therefore: open writer once per tick → do **all** of this tick's acks/sends/polls under that one handle → drop. Contention with a concurrent writer surfaces as `store/lock`, mapped to `exec/store`, and the loop backs off and retries on the next tick rather than failing the run.
- **That open/drop is not free, and batching is why it is affordable.** `Store::open` folds the journal (or loads the newest snapshot and folds the tail), and `Drop for Store` writes a snapshot whenever the store is writable and non-empty. A tick that settles ten directives therefore pays one fold and one snapshot, not ten; a tick with nothing to write opens no writer at all and pays nothing. Never open the writer inside a per-directive loop.
- `fsm execute --check --handlers <file>`: validate the table and print the resolved handler list, then exit 0 — the operator's pre-flight. It touches no data dir.
- **Two entry points, because two callers own the writer differently.** `service::tick_with(&mut Watcher, &mut Scheduler, &mut Runner, &mut Pipeline, &mut Store, &mut dyn Clock, now_ms) -> Vec<String>` does the work against a writer handle it is *lent*; `service::tick(.., &Path /*data_dir*/, ..)` opens the writer, calls `tick_with`, and drops it. `run` calls `tick`; embedded mode (task `3902`) calls `tick_with` with the handle `serve` already holds, because a second `Store::open` in that same process would collide with serve's own lock. Tests that drive a writer themselves must **drop that handle before calling `tick`**, for exactly the same reason — the lock is per data dir, not per process. The clock and `now_ms` are both parameters on purpose: `run` reads `now_ms` from the clock **once** per tick so every decision in that tick sees one time, while the store's `_on` mutators go on consuming clock ticks of their own as they journal — under `FixedClock`, whose `now_ms` advances on each call, folding the two would make a tick's decisions depend on how many records it happened to write. `service::run` is the thin `loop { tick(..); sleep(..) }` wrapper around it; both live in `fsm-execute/src/service.rs` — `tick` from task `3802`, `run` from task `3901` — so embedded mode reuses them rather than reimplementing a driver. The golden session (workstream 0040) drives discrete ticks with a `FixedClock` and byte-compares an abstract trace, independent of wall-clock or a real subprocess.
- Action lines are the golden's payload, so they carry **identifiers only** — effect name, effect id, request id, event name, outcome. Never an absolute path, a pid, a temp dir, or a duration: those differ per machine and per run, and a golden that contains one cannot be byte-compared.

Coordination with `fsm serve` (task `3902`) resolves the only genuine fork in the plan: **who else may write while the executor runs?** Three modes, decided here by their lock behaviour, with **standalone-paired as the default**:

| Mode | Writer of acks | `fsm serve` state while executor runs | When to use |
|---|---|---|---|
| `embedded` | the `serve` process itself, inline | holds the writer lock; runs effects on its single thread | single operator ad-hoc session; simplest; a hung handler blocks MCP, and ticks happen only when a client sends a line |
| `paired` (default) | the executor process | runs **read-only** (`open_read_only`) for monitoring | the headline case — the MCP host watches progress while the executor drives the workflow unattended |
| `exclusive` | the executor process | not running | unattended batch/CI where nothing else reads that store |

- **`paired` is the default and the recommended deployment.** The MCP host (`fsm serve`) is started read-only for the shared data dir so the LLM can call `instance_get`/`instance_history`/`instance_list` and watch the executor's journaled acks and transitions in real time, while only the executor holds the writer lock. `fsm serve` therefore needs a `--read-only` flag (new in the `SERVE` spec in `args.rs`) that opens `Store::open_read_only` instead of `Store::open`.
- **Six tools mutate, not four.** Everything gated by `ensure_writable()` must answer read-only cleanly: `machine_create`, `instance_create`, `instance_send`, `deadline_poll`, `effect_ack`, and `instance_cancel`. Task `3902` names that set once as `pub const MUTATING_TOOLS` beside the tool registry, `dispatch` consults it instead of six match arms, and task `4101`'s doc test imports the same constant — so the list cannot drift between the gate and the docs. Count them from the code (`store/lifecycle.rs`, `store/instance/*.rs`), not from memory — `machine_create` is the easy one to forget, and it is the *authoring* path, so forgetting it means the model gets an unexplained failure at the exact moment it is being most useful. Each returns a clean `io/write`-mapped tool error whose hint names read-only mode and says the executor owns writes. `machine_create` with `dry_run` validates without writing and therefore still works. Read tools (`machine_list`, `machine_get`, `machine_analyze`, `machine_diagram`, `instance_get`, `instance_list`, `instance_history`, `simulate`) work unchanged.
- **What paired mode costs, stated plainly:** while a read-only serve is up, the model can watch but cannot author, create, trigger, cancel, or ack. Defining the machine and sending the trigger event are writes, so they happen either **before** the executor starts, or through a writer path that takes the lock between ticks (`fsm machine add`, `fsm instance new`, `fsm instance send` from a terminal, which contend for one tick at worst), or in `embedded` mode. Task `4101` documents this sequence as the normal way to start a run; it is the one real ergonomic price of single-writer, and the plan states it rather than discovering it in front of a user.
- **`embedded`** is an opt-in `fsm serve --execute --handlers <file>` that runs the very same scheduler/runner/pipeline on the serve thread, calling `service::tick` once per protocol iteration against serve's own writer handle. Two limits, both documented rather than papered over: a long-running handler blocks the protocol, and — because `serve_session` blocks in `read_capped_line` until the client sends a line — **a tick happens only when the client speaks**. Embedded mode therefore advances a workflow during a conversation, not overnight; that is precisely why it is not the default and why the unattended claim belongs to `paired`/`exclusive`. It shares 100% of the `fsm-execute` library code — only the driver differs.
- **`exclusive`** is just the executor alone against a data dir; no serve. It is the zero-configuration path and what the chaos harness uses. It differs from `paired` in exactly one behaviour: at startup it asserts it can take the writer lock, and fails with `exec/mode` if something else already holds it, instead of backing off and retrying.
- The mode is recorded as a one-line startup log by `fsm execute`/`fsm serve`, and in `serve`'s `instructions` adjunct. That line is **not** part of any tick trace (0039's identifier-only rule), so a mode default changing under task `3902` cannot invalidate task `4001`'s golden. The decision rule the docs state: **if an LLM must watch progress live, run serve `--read-only` (paired); otherwise run the executor alone (exclusive); use embedded only for a single ad-hoc session.**

## 0040 — Proof

Two suites make "unattended and resumable" a checkable claim rather than prose.

**The stub handler is a Rust binary, never a shell script.** CI runs the whole suite on Windows as a full test leg (`.github/workflows/ci.yml`, CONTRIBUTING §Verification and portability), so a `.sh` fixture is not a fixture — it is a red Windows job. Use the precedent `crash_harness.rs` already sets: the test **re-executes its own test binary** (`std::env::current_exe()`) with a marker argument, and an early return at the top of the test file plays the stub role — print a fixed line to stdout and one to stderr, exit with the requested code, optionally append to the path in an env var. That is cross-platform, ships no extra artifact, and needs no exec bit. Because the resolved path differs per machine, the committed handler table is a **template** (`handlers.template.json`) whose `argv[0]` placeholder the test replaces when it materializes the table into the temp dir; the golden trace never contains the path (0039's identifier-only rule), so it stays byte-comparable.

Golden two-process session (task `4001`): fixtures-first `crates/fsm-cli/tests/fixtures/executor/`. Drive a real `Store` in a temp dir with `FixedClock`: define a machine that emits an effect on entering a state (modelled on `order_lifecycle`'s `request_confirmation`, whose advance event declares a stamped field — so the fixture exercises `on_ok.stamps` rather than pretending advance events are field-less), create an instance, advance it so the effect is pending — then, instead of a chat turn acking it, run `service::tick` against the stub. The `.expected` stream is the hand-derived sequence of abstract tick lines: `observed pending request_confirmation …` → `spawned handler …` → `acked ok request_id=exec-ack-…` → `sent confirmed request_id=exec-ev-…` → `instance reached terminal`. It must show the derived `request_id`s (proving idempotency is engaged) and must run **without** wall-clock sleeps by driving ticks explicitly.

Chaos harness (task `4002`): `crates/fsm-cli/tests/executor_chaos.rs`, self-contained seeded xorshift64* generator (the deliberate ~30-line duplication with plan 0007's suites is documented in the file header, matching precedent). Each of 200 seeded iterations (floor 200, raised by `FSM_EXECUTOR_CHAOS_ITERS`, mirroring `FSM_CRASH_ITERS`): fresh temp data dir → a machine with one effect → drive N ticks interleaving *simulated executor death* at each named point: (a) after spawn before reap, (b) after reap before ack, (c) after ack before advance-send, (d) mid-poll. Death is simulated by dropping the runner/pipeline and constructing a *fresh* executor against the same data dir — the honest word is **restart**, not `kill -9`: real signal-kill coverage of the journal already lives in `crash_harness.rs`, and what this harness proves is that a fresh executor's *journal-derived* decisions resume correctly.

The invariant is stated in the shape the design actually guarantees — **at-least-once execution, exactly-once journaling** — because "the handler never runs twice" is false at death point (a) and claiming it would make the suite either wrong or vacuous:

- the journal verifies clean, and no tick panics;
- for **every** death point, the instance holds **exactly one** `effect_acked` record per effect id, and at most one advance `event_applied` per `(effect_id, event)`;
- for death points (c) and (d) — where the ack is already journaled — the recording stub's side file lists the effect **at most once**;
- for death points (a) and (b) — both *before* the ack — the side file may list it **twice**, and that second run is the documented at-least-once boundary (§0038's orphan rule); the assertion is that the journal still shows one ack. The line runs through the ack, not through the reap: reaping a child puts its outcome in memory, and a restart is precisely what loses memory, so a successor that finds a pending effect with an unclaimed key has no way to know the handler already ran and must run it again;
- the instance ends coherent: terminal, or still pending with a resumable effect — never a state the engine would reject.

`EXECUTOR_CHAOS_SEED` replays one seed; failures print it. Budget note for whoever adds iterations: the 45-minute CI ceiling is already dominated by `crash_harness.rs`'s 1,000 spawns per profile, run across two profiles and three operating systems, and Windows process creation is several times costlier than Unix.

## 0041 — Docs

`docs/EMBEDDING.md` gains its normative *Executing workflows* section (task `4101`), `docs/API-POLICY.md` gains the row a fifth crate owes its readers, and `README.md` gains one row in the guarantees/honest-non-claims area plus a 4-line `fsm execute` demo mirroring the 60-second MCP demo. The section documents, in this order:

1. The outbox contract restated for operators: effects are emitted; **you** (now via `fsm execute`) run them and ack; acks never transition; the advance event is one the machine already declares, named in the handler table, never improvised.
2. The handler-table format `fsm.handlers/1` in full — every field including `on_ok`/`on_failed`, the no-shell/no-splitting guarantee, the default-deny behaviour, and the bounded-output digest and lossy-UTF-8 rules.
3. The idempotency rules an operator must know: `request_id` derivation, why a restarted executor is safe, and why a *changed* result under a recycled key gets refused, not replayed.
4. The three run modes and the decision rule, including `fsm serve --read-only`'s effect on every tool in `MUTATING_TOOLS` — and the sequence that follows from it: author and trigger through a writer, then let the executor run while the model watches.
5. The honest non-claims: the executor is **single-node and at-least-once at the process boundary**. An ack journalled but an advance-send lost is re-derived and replayed, never double-applied; a handler killed mid-run is re-run by the next executor, so a handler that already reached the outside world is *not* rolled back by `fsm` — model the undo as an explicit compensating effect in the machine and let the failure path emit it. No HA, no multi-writer, no handler distribution.
6. `docs/API-POLICY.md`: `fsm-execute` joins the per-crate support table. It is a library, but its surface is this plan's own — state whether an embedder may depend on it, alongside the existing `fsm-core`/`fsm-store`/`fsm-cli` rows, and keep the zero-dependency paragraph's crate list accurate.

A mechanical test `crates/fsm-cli/tests/executor_doc.rs` pins: the string `fsm.handlers/1` appears in EMBEDDING.md; each `exec/*` code string defined in the crate appears in the doc; and the README's `fsm execute` demo block names `--handlers`, the data-dir flag, and the `serve --read-only` pairing, so the operator-facing surface cannot silently drift from the docs.
